# Code-XR Architecture

> **Purpose**: High-level system architecture for AI agents and developers. Read this before touching anything under `src/`.
> **Stability**: Stable — update only when the architecture itself changes (new module, changed data flow), not for feature-level changes.
> Facts here were verified against the code on 2026-07-08; the module map and every path were re-verified on 2026-11-25 (story #43) after the monorepo move and the feature-first `src/` layout (#55). Items marked *[inferred]* are conclusions from structure/naming, not verified line-by-line.

## The one-paragraph summary

CodeXR is a VS Code extension (291 TS files under `src/`, in five layers since #55) that analyzes source code with a **Python backend** (its own code-metrics analyzer, `backend/src/tools/code_metrics/`, which replaced Lizard in 1.2.1; run in a managed virtual environment) and renders the results as **BabiaXR/A-Frame XR scenes** served by **local HTTP/HTTPS servers** with **SSE live-reload**. The extension side is TypeScript; the in-scene runtime is plain JavaScript living in `templates/components/` and injected into generated HTML.

## Main data flow (the pipeline)

```
User command (context menu / tree / palette)
  └─> src/features/analysis/commands/...        (per-mode command handlers)
      └─> src/core/analysis/analysisOrchestrator.ts → session/sessionRegistry.ts (one session per targetKey)
          └─> launch/launchKinds.ts resolveLauncher(kind, targetType)
              └─> launchers/launcherXRAnalysis.ts | launcherLivePanel.ts | launcherVisualizeDOM.ts
          └─> launchers/launchPipeline.ts  → one transaction under launch/launchControl.ts
                (abort signal + 10 min deadline + teardown stack; process → save → server → watcher)
              ├─> python/executePython.ts   → spawns managed venv, runs python/main.py → JSON metrics
              ├─> src/core/charts/                → validates dimension mapping, fills HTML template
              │     (chart registry + placeholder processing over templates/xr/...)
              ├─> scene-assets/*ComponentAsset.ts
              │     → inlines browser runtimes from templates/components/**/*.js into the HTML
              └─> session-servers/serverLaunchOrchestrator.ts (SSE + file map keyed by session id)
                    └─> src/core/server (HTTP/HTTPS) serves the scene
                        └─> registered in src/core/server/registry → shown in sidebar tree (src/features/active-servers)
Live updates: core/analysis/watchers/* detect file changes → re-run Python →
  src/core/server/sse/SSEManager.ts (by session id) → browser reloads data
```

Analysis types (what the table shows) and launch kinds (how a page is served) are descriptors in `core/analysis/launch/` (`analysisTypes.ts`, `launchKinds.ts`, `storageFolders.ts`); the server-capability, controller-view and snapshot-probe tables are derived from them. Checklist: `apps/vscode-extension/docs/adding-an-analysis-type.md`.

Three analysis modes share this pipeline: **XR** (A-Frame scene in browser/headset), **LivePanel** (2D webview panel), **DOM visualization** (HTML DOM structure in XR). Each mode has its own launcher and parser (`core/analysis/parsers/`); one shared requirement processor (`core/analysis/processors/FileRequirementProcessor.ts` → `analysisBootstrap.ts`) loads the templates the mode needs.

## Activation flow (`src/extension.ts`)

1. `initializeExtensionContext`, `initializeHost(createVSCodeHost(context))` (#13: the core's host seam, see the module map), `setLaunchNotifier(launchNotifications)` (the post-launch toasts `core/server/multiServerLauncher.ts` shows, registered from `features/active-servers` so the core never imports a feature) and `setServerPanelCloser` (how `ServerControl` closes a stopped server's lateral panel, over `platform/webview/panelManager.ts`) and `CodeXRLogger.initialize` (`src/platform/`). The logger attaches the "CodeXR" output channel to the vscode-free log sink; everything logged before this (including at module load) was buffered by the sink and is flushed into the channel now.
2. Singletons initialized: `AnalysisConfigurationStorage`, `CollaborationProfileManager`, `RemoteAccessManager`, `ServerSettingsManager`, `getActiveServerRegistry()`, `ServerControl`.
3. `ModularTreeDataProvider` (`src/app/sidebar/ModularTreeDataProvider.ts`) registered as the single tree view `codexrTree` (one activity-bar container hosts all sections: servers, active servers, examples, visualize data, analyses, python env, visualization settings, learn more). **Collaboration is not a root section**: `CollaborationSectionProvider` is mounted by `ActiveServersSectionProvider` as the nested `COLLABORATION` group (item type `collaboration-group`), so its items — including `Join Remote Session` — render inside `ACTIVE SERVERS`.
4. `registerAllCommands` (`src/app/commands/registerAllCommands.ts`) merges command arrays from every feature module and registers them via `CommandBuilder.registerAll`. **`assertUniqueCommandIds` throws on duplicate command IDs** — keep this in mind when adding commands.
5. `StartupCoordinator` (`src/app/startup/startupCoordinator.ts`, max 3 concurrent) defers heavy work: restore server settings + ensure HTTPS cert pair, init `ServerWatcherIntegration`, init Python env + prefetch XR field schema, clean stale analysis artifacts.

`deactivate()` tears down remote access, the active-server registry, the SSE manager + `fileToServerMap`, and the tree provider.

`activationEvents` in package.json is empty — activation is driven by contributed commands/views.

**Layout** (story #55, `docs/cleanup/src-layout.md` §3; pinned by `test/tooling/srcLayout.test.cjs`): `src/` holds `extension.ts` and five layers, `app/` (composition root) → `features/` (one folder per sidebar section) → `core/` (the engine, one folder per domain) → `platform/` (VS Code host plumbing, no feature knowledge) → `shared/` (no VS Code, no domain). Folder names are kebab-case; `core/` and `features/` hold folders only; there are no re-export barrels.

**Per-feature layout convention**: `features/<section>/` has `commands/` (`<x>Commands.ts`, the handlers, and `<x>CommandRegistrations.ts`, the registration array `app/commands/registerAllCommands.ts` collects), `views/` (the `*SectionProvider.ts`, item factories and click handlers, flat), and where needed `services/` and `model/`. A section with subsections nests them under `sections/<subsection>/` (see `features/analysis/`). Engine code that more than one feature, the servers or the analysis pipeline uses goes in `core/<domain>/`, not in a feature. When adding a feature, mirror this pattern.

**Folder dependencies** (stories #42, #55): which folder may import which is data in `test/tooling/folderDependencies.json`, checked by `test/tooling/dependencyDirection.test.cjs` (type imports count). A folder is the first directory under `src/`, or the first two under `core/` and `features/` (`twoLevelAreas`); the same file holds the layer order `app → features → core → platform → shared` (`layers`), which the test enforces (no upward edge, no feature importing another feature) except for the reasoned entries in `layerExceptions`. A new cross-folder direction fails the gate until it is added there; a new two-way pair also needs a written reason. The remaining pairs are each documented in that file (all inside the server/analysis subsystems: `core/server`, `core/remote-access`, `core/analysis` with `core/history`, plus `core/server`/`features/active-servers`, which is the one allow-listed upward edge). `platform/` imports no feature folder, and `core/` none besides that edge.

**Barrel policy** (decided 2026-09-18, measured): 82% of the relative imports in `src/` (807 of 981) already name a concrete file, and 32 of the 82 `index.ts` barrels have no importer at all. So: **import the concrete file; do not add a barrel "for symmetry"**. An unimported barrel is dead code and keeps otherwise-dead modules looking referenced. Story #55 (batch 0) dissolved every re-export barrel that was left: `src/` has none, and the two `index.ts` files that held code are renamed in the move.

**Export convention**: export what another file or a test consumes. A symbol used only inside its own file does not need `export`; an exported symbol with no consumer anywhere in `src/` **and** `test/` is dead (tests load compiled code from `out/`, so a test-only consumer counts as a consumer).

Note: before #55 a feature was split between a feature folder and `views/<feature>/` (e.g. `active_servers/views/` **and** `views/active_servers/`); the moves put both halves in `features/<feature>/views/`. `src/app/sidebar/` and `src/app/commands/registerAllCommands.ts` are the current *aggregation points*; per-module `views/`/`commands/` folders are the feature implementations they pull from. *[inferred from import wiring]*

## Cross-module contracts (the seams that matter)

1. **XR field schema**: Python defines analyzable fields in `backend/src/utils/xr_field_schema.py`; TypeScript consumes it via `core/analysis/python/xrFieldSchemaService.ts` (backed by `main.py --mode schema`). Dimension-mapping validation in `core/charts/processing/dimensionValidator.ts` checks user mappings against this schema. **Changing metrics on the Python side requires keeping this schema in sync.**
2. **Chart registry**: `core/charts/chartRegistry.ts` (`BabiaChartRegistry` singleton) is the source of truth for available chart types and their dimension requirements.
3. **File ↔ server mapping**: `src/core/server/fileToServerMap.ts` links analyzed files to the server instance serving their visualization; SSE clients are keyed by file URI in `SSEManager`.
4. **Component-asset injection**: TS files in `core/analysis/scene-assets/*ComponentAsset.ts` read runtime JS from `templates/components/` and inline it into generated HTML. A runtime shipped as one file is a row of the `SINGLE_FILE_RUNTIME_ASSETS` descriptor table in `scene-assets/singleFileRuntimeAssets.ts` (output name, folder, refusal label), and its `*ComponentAsset.ts` is a thin wrapper keeping the named exports; multi-part runtimes go through `runtimeAssembly.ts`. The browser runtimes never import TS code; the contract is the injected globals and entity schemas (see `templates/components/COMPONENTS.md`).
5. **Command registration**: every module exports a command-registration array consumed by `src/app/commands/registerAllCommands.ts`. Command IDs use prefixes `codeXR.*` / `codexr.*` (both exist — check before adding).

## Logging (since 1.2.1)

Every diagnostic of the extension host goes through `src/platform/logging`. A module logs with `const logger = getLogger('SCOPE')` from `platform/logging/sink.ts`, which has no `vscode` import, so any module (and any unit test that loads it from `out/` without the fake vscode) can log. Lines land in the **CodeXR** output channel as `[ISO time] [LEVEL] [SCOPE] message`, with an optional metadata line (an Error's stack, a string, or JSON).

- **Levels.** `warn` and `error` are always written. `debug` and `info` are written only in development mode or with `codeXR.debug.verboseLogs` on (`logPolicy.ts`). Anything carrying a file system path is `debug`, passed lazily (`logger.debug(() => ...)`), so it costs nothing while verbose logging is off. A caught failure is reported at `warn` or `error`, never only at `debug`.
- **Before activation** the sink keeps up to 1,000 lines in a buffer and flushes them through the level policy when `CodeXRLogger.initialize` attaches the channel; while no channel is attached (and after it is disposed), `warn`/`error` are also echoed to the console.
- **No `console.*` in `src/`.** ESLint's `no-console` is an error for `src/**/*.ts`; `sink.ts` is the only allowlisted file (its console fallback). Browser runtimes under `templates/` are not extension-host code and keep their own (gated) console output.
- `observeLogEntries` on the sink is a test seam: characterization suites record what a module logs (`test/helpers/logCapture.cjs`). Nothing in the extension observes.

## How future agents should use this document

- Use the module map to jump straight to the right folder instead of scanning `src/` (`core/analysis/` and `features/analysis/` together are about 120 files).
- Use the "cross-module contracts" section to know what else must change when you touch a seam (especially Python metrics ↔ field schema ↔ dimension validation).
- For feature-specific depth (dependency graph, historical comparison, project evolution, remote access), read the existing docs in `docs/` — this file deliberately does not duplicate them. See `INDEX.md` for the task → docs mapping.
